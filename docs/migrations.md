# Database and Authentication migrations

This is the promotion ledger for changes that affect Cloud SQL/Data Connect or Firebase
Authentication. Application code must not depend on a production database or Authentication
change until the corresponding migration has been applied and verified in test.

## Workflow

1. Add a row before changing the test environment. Use an ID in the form `MIG-YYYYMMDD-NNN`.
2. Record the exact schema, data, provider, claim, blocking-function, or user transformation.
3. Apply it to `student-assessment-test` first and record the command or deployment plus evidence.
4. Leave production status as `Pending` until release approval and a verified production backup.
5. During production release, apply the same reviewed migration and record its timestamp and evidence.
6. Prefer a forward-fix. Document a rollback before any destructive or irreversible migration.

Authentication migrations include provider/configuration changes, blocking functions, MFA policy,
custom-claim shape changes, and bulk user transformations. Routine user sign-up and ordinary
application data changes are not migrations.
